Replacing Abp's DI Framework with DryIoc

2018-11-2010 min read#C# #ABP #AspNetBoilerplate #Dependency Injection #DryIoC #Castle Windsor

#1. Background

You might ask: Castle Windsor works fine, so why go to all the trouble of replacing it with DryIoc? The answer is performance. DryIoc is a good, lightweight DI framework. The whole project is just two source files, around 10,000 lines in total (PS: most of that is comments).

In the performance benchmarks of the various IoC containers, DryIoc does very well, and that’s why I picked it. The Castle Windsor that Abp uses is very slow when it resolves complex objects, and after switching to DryIoc it got more than 150% faster.

[Note]

This post only changes and tests the .NET Core libraries. I didn’t touch or test the .NET Framework ones.

#2. Preparation

Here’s what you need:

  1. A copy of the Abp source code.
  2. A project to test with.
  3. Visual Studio 2017 or Rider.
  4. One .NET developer.

#3. Analysis

First, most of what the Abp framework does goes through the IIocManager interface. It’s an abstraction layer that acts as the DI framework’s operation class. Its default implementation uses Castle Windsor to register and resolve components, so all we need to do is make it use a DryIoc container instead.

Second, Abp uses Castle Windsor’s IWindsorContainer object in a lot of places. In most of them it’s used to register components or to hook the component registration event, and we can reimplement all of that ourselves.

Once that’s done, all Abp components can be registered and resolved through DryIoc. To integrate with ASP.NET Core we still need an IServiceProvider adapter, and DryIoc already provides one, so we can just use it.

So the projects we need to change are the core Abp library and the Abp.AspNetCore module. Besides those two, the Abp.EntityFrameworkCore libraries need changes too, because they also use the IWindsorContainer object directly to work with the container.

#4. Let’s Get Started

#4.1 Changing the Abp Library

Almost everything that needs changing in the Abp library is in the Dependency folder. I’ve covered this folder before. It holds basically all the dependency injection types and interfaces.

Besides the dependency injection types, we also need to change the places where interceptors get attached. Before, when Abp wanted to attach an interceptor to a type, it used the component registration event provided by the IWindsorContainer interface.

First, add a NuGet reference to the DryIoc package in the Abp library. I installed version 3.1.0-preview-06.

#4.1.1 Changing IocManager

Let’s start with the IIocManager interface. It’s defined like this:

C#
/// <summary>
/// This interface is used to directly perform dependency injection tasks.
/// </summary>
public interface IIocManager : IIocRegistrar, IIocResolver, IDisposable
{
	/// <summary>
	/// Reference to the Castle Windsor Container.
	/// </summary>
	IWindsorContainer IocContainer { get; }

	/// <summary>
	/// Checks whether given type is registered before.
	/// </summary>
	/// <param name="type">Type to check</param>
	new bool IsRegistered(Type type);

	/// <summary>
	/// Checks whether given type is registered before.
	/// </summary>
	/// <typeparam name="T">Type to check</typeparam>
	new bool IsRegistered<T>();
}

It has an IWindsorContainer property, and we change that to IContainer. Once you do this, a pile of errors will show up in the other Abp projects. Don’t panic, we’ll go step by step.

Next, go to IocManager, the implementation of IIocManager. Change the type of IocContainer to IContainer there as well, then look at the constructor, which has the following code:

C#
public IocManager()
{
    IocContainer = CreateContainer();
    _conventionalRegistrars = new List<IConventionalDependencyRegistrar>();

    //Register self!
    IocContainer.Register(
        Component
        .For<IocManager, IIocManager, IIocRegistrar, IIocResolver>()
        .Instance(this)
    );
}

Since IocContainer has changed, we can’t use the CreateContainer() method to create the DryIoc container any more. The self-registration below also uses the IWindsorContainer registration API, so that needs to change too. The updated constructor looks like this:

C#
public IocManager()
{
    // Rules turns on tracking of disposable transients here. It's off by default.
    IocContainer = new Container(Rules.Default.WithTrackingDisposableTransients());
    _conventionalRegistrars = new List<IConventionalDependencyRegistrar>();

    // Register itself
    IocContainer.UseInstance(typeof(IocManager),this);
    IocContainer.UseInstance(typeof(IIocManager),this);
    IocContainer.UseInstance(typeof(IIocRegistrar),this);
    IocContainer.UseInstance(typeof(IIocResolver),this);
}

Next, look at the methods that still show errors. One is ApplyLifestyle, a private helper for the registration methods. It converts the lifestyle Abp defines into the lifetime constant of the specific IoC container. It used to return a ComponentRegistration<T>, which is a Castle Windsor class, so it needs to change. After the change it looks like this:

C#
private static IReuse ApplyLifestyle(DependencyLifeStyle lifeStyle)
{
	switch (lifeStyle)
	{
		case DependencyLifeStyle.Transient:
			return Reuse.Transient;;
		case DependencyLifeStyle.Singleton:
			return Reuse.Singleton;
		default:
			return Reuse.Transient;
	}
}

After that, what’s left is changing the registration and resolve methods. The registration and resolve methods on IocManager just call the underlying IoC container, and DryIoc’s IContainer provides almost everything IWindsorContainer does. Only a few methods are different.

Here are some of the updated registration and resolve methods (see the code on GitHub for all of them):

C#
public void Register(Type type, DependencyLifeStyle lifeStyle = DependencyLifeStyle.Singleton)
{
	IocContainer.Register(type,ApplyLifestyle(lifeStyle));
}

// ... other methods
public void Register(Type type, Type impl, DependencyLifeStyle lifeStyle = DependencyLifeStyle.Singleton)
{
	if (type == impl)
	{
		// The made parameter tells DryIoc to prefer the constructor whose arguments it can resolve
		IocContainer.Register(type,impl,ApplyLifestyle(lifeStyle),
			made: Made.Of(FactoryMethod.ConstructorWithResolvableArguments));
		RegisterTypeEventHandler?.Invoke(this,type,impl);
	}
	else
	{
		IocContainer.RegisterMany(new[]
			{
				type,
				impl
			},
			impl,
			made: Made.Of(FactoryMethod.ConstructorWithResolvableArguments),
			reuse: ApplyLifestyle(lifeStyle));
		
		RegisterTypeEventHandler?.Invoke(this,type,impl);
		RegisterTypeEventHandler?.Invoke(this,impl,impl);
	}
}

// ... other methods

One thing to watch out for is the resolve method that takes arguments, public T Resolve<T>(object argumentsAsAnonymousType). Unlike Castle Windsor, DryIoc only accepts an array of arguments, not an anonymous object holding a set of arguments. So we need to change the parameter to object[]. Since this changes the method signature, we also have to change the signatures of the resolve methods that take arguments in ScopedIocResolver, IIocResolver and IocResolverExtensions.

C#
public T Resolve<T>(object[] argumentsAsAnonymousType)
{
    return IocContainer.Resolve<T>(argumentsAsAnonymousType);
}

Another one is public T[] ResolveAll<T>(), which calls IocContainer.ResolveAll internally. DryIoc doesn’t have that method, but it has ResolveMany(), which does the same thing. Here are all the overloads of ResolveAll() after the change:

C#
///<inheritdoc/>
public T[] ResolveAll<T>()
{
	return IocContainer.ResolveMany<T>().ToArray();
}

///<inheritdoc/>
public T[] ResolveAll<T>(object[] argumentsAsAnonymousType)
{
	return IocContainer.ResolveMany<T>(args:argumentsAsAnonymousType).ToArray();
}

///<inheritdoc/>
public object[] ResolveAll(Type type)
{
	return IocContainer.ResolveMany(type).ToArray();
}

///<inheritdoc/>
public object[] ResolveAll(Type type, object[] argumentsAsAnonymousType)
{
	return IocContainer.ResolveMany(type, args:argumentsAsAnonymousType).ToArray();
}

There’s also Release for releasing objects. DryIoc has no release method, so the only option is to call the object’s Dispose() method explicitly.

C#
public void Release(object obj)
{
    if(obj is IDisposable disposeObj)
    {
        disposeObj.Dispose();
    }
}

After these changes, there’s still one place showing an error:

C#
public void RegisterAssemblyByConvention(Assembly assembly, ConventionalRegistrationConfig config)
{

	{
		registerer.RegisterAssembly(context);

If you’ve read my earlier posts on the Abp source code, you’ll know that what Install() does is quite simple. It goes through the types of the given assembly, looks for objects that implement the IWindsorInstaller interface, and calls their Install() method. Inside that Install(), the registration is usually done through the IIocContainer or IIocManager object that gets passed in.

Here we can write two extension methods Intsall() for IocManager, plus an IDryIocInstaller interface, to get the same behavior.

C#
namespace Abp.Dependency
{
    public interface IDryIocInstaller
    {
        void Install(IIocManager iocManager);
    }
}

The extension methods:

C#
using System;
using System.Linq;
using System.Reflection;

namespace Abp.Dependency
{
    public static class IocManagerExtensions
    {
        public static void Install(this IIocManager iocManager,IDryIocInstaller installer)
        {
            installer.Install(iocManager);
        }

        public static void Install(this IIocManager iocManager, Assembly assembly)
        {
            // Get all the installer types in the given assembly
            var installers = assembly.GetTypes().Where(type => type.GetInterfaces().Any(@interface => @interface == typeof(IDryIocInstaller)));

            // Go through the types, create each one with Activator and call it
            foreach (var installer in installers)
            {
                (Activator.CreateInstance(installer) as IDryIocInstaller)?.Install(iocManager);
            }
        }
    }
}

Now go back to the place that showed the error at the start, and change its Install() call to use our new extension method.

C#
public void RegisterAssemblyByConvention(Assembly assembly, ConventionalRegistrationConfig config)
{

    foreach (var registerer in _conventionalRegistrars)
    {
        registerer.RegisterAssembly(context);

    if (config.InstallInstallers)
    {
        // Call the extension method we wrote earlier
        this.Install(assembly);
    }
}

#4.1.2 Changing the Dependency Injection Helper Interfaces

The Abp library provides two interfaces (ITransientDependency and ISingletonDependency) that let you register an object quickly. Together with the AddConventionalRegistrar() and RegisterAssemblyByConvention() methods of IocManager, they can register all the types in an assembly that match the convention. (PS: this flow is a lot like the Installer approach from before)

With Castle Windsor, Abp didn’t have to do much to get this working. DryIoc doesn’t provide such high-level features, but the idea isn’t complicated: scan all the types in the assembly and check them one by one.

The original BasicConventionalRegistrar automatically registered types that implement ITransientDependency, ISingletonDependency or IInterceptor. So we end up with the following implementation:

C#
using System;
using System.Linq;
using System.Reflection;
using Abp.Extensions;
using Castle.DynamicProxy;

namespace Abp.Dependency
{
    public class AssemblyType
    {
        public Type ServiceType { get; set; }

        public Type ImplType { get; set; }
    }
    
    /// <summary>
    /// This class registers types that implement <see cref="ITransientDependency"/> and <see cref="ISingletonDependency"/>.
    /// </summary>
    public class BasicConventionalRegistrar : IConventionalDependencyRegistrar
    {
        public void RegisterAssembly(IConventionalRegistrationContext context)
        {
            // Register transient objects
            var waitRegisterTransient = GetTypes<ITransientDependency>(context.Assembly).ToList();

            foreach (var transientType in waitRegisterTransient)
            {
                context.IocManager.RegisterIfNot(transientType.ServiceType,transientType.ImplType,DependencyLifeStyle.Transient);
            }
            
            // Register singleton objects
            var waitRegisterSingleton = GetTypes<ISingletonDependency>(context.Assembly).ToList();

            foreach (var singletonType in waitRegisterSingleton)
            {
                context.IocManager.RegisterIfNot(singletonType.ServiceType,singletonType.ImplType,DependencyLifeStyle.Singleton);
            }
            
            // Register Castle.DynamicProxy interceptors
            var waitRegisterInterceptor = GetTypes<IInterceptor>(context.Assembly).ToList();

            foreach (var interceptorType in waitRegisterInterceptor)
            {
                context.IocManager.RegisterIfNot(interceptorType.ServiceType,interceptorType.ImplType,DependencyLifeStyle.Transient);
            }
        }

        private ParallelQuery<AssemblyType> GetTypes<TInterface>(Assembly assembly)
        {
            Type GetServiceType(Type type)
            {
                var interfaces = type.GetInterfaces().Where(i => i != typeof(TInterface));

                // Prefer the interface whose name matches the type name with the I removed
                var defaultInterface = interfaces.FirstOrDefault(i => type.Name.Equals(i.Name.RemovePreFix("I")));
                if (defaultInterface != null) return defaultInterface;
                if (interfaces.FirstOrDefault() != null) return interfaces.FirstOrDefault();
                return type;
            }

            return assembly.GetTypes()
                .AsParallel()
                .Where(type => typeof(TInterface).IsAssignableFrom(type))
                .Where(type => type.GetInterfaces().Any() && !type.IsInterface)
                .Where(type => !type.IsGenericTypeDefinition)
                .Where(type => !type.IsAbstract)
                .Select(type => new AssemblyType
                {
                    ServiceType = GetServiceType(type),
                    ImplType = type
                });
        }
    }
}

In our new registration convention, the core of it is the GetTypes() method, which has the fairly complicated checking logic. The transient and singleton registration is just a call to the registration methods of the IIocManager interface.

#4.1.3 Binding Interceptors

We’re no longer using Castle Windsor, so how do we use interceptors, and how do we bind them to types?

The DryIoc docs say that its interception is also built on Castle Dynamic Proxy, so all we need is a static extension class as a helper.

C#
using System;
using System.Linq;
using Castle.DynamicProxy;
using DryIoc;
using ImTools;

public static class DryIocInterception
{
    static readonly DefaultProxyBuilder ProxyBuilder = new DefaultProxyBuilder();

    public static void Intercept(this IRegistrator registrator,Type serviceType,Type interceptorType,Type implType, object serviceKey = null)
    {
        // Check whether the type passed in is an interface or a class, so we can build the proxy type
        Type proxyType;
        if (serviceType.IsInterface())
            proxyType = ProxyBuilder.CreateInterfaceProxyTypeWithTargetInterface(
                serviceType, ArrayTools.Empty<Type>(), ProxyGenerationOptions.Default);
        else if (serviceType.IsClass())
            proxyType = ProxyBuilder.CreateClassProxyTypeWithTarget(
                serviceType, ArrayTools.Empty<Type>(), ProxyGenerationOptions.Default);
        else
            throw new ArgumentException(
                $"Intercepted service type {serviceType} is not a supported, cause it is nor a class nor an interface");

        // Create the DryIoc decorator
        var decoratorSetup = serviceKey == null
            ? Setup.DecoratorWith(useDecorateeReuse: true)
            : Setup.DecoratorWith(r => serviceKey.Equals(r.ServiceKey), useDecorateeReuse: true);

        // Replace the original registration so the interface resolves to the new proxy type
        registrator.Register(serviceType, proxyType,
            made: Made.Of((Type type) => type.GetConstructors().SingleOrDefault(c => c.GetParameters().Length != 0), 
                Parameters.Of.Type<IInterceptor[]>(interceptorType.MakeArrayType()),
                // Don't leave this out, or property injection won't work
                PropertiesAndFields.Auto),
            setup: decoratorSetup);
    }
    
    public static void Intercept<TService,TImplType, TInterceptor>(this IRegistrator registrator, object serviceKey = null) 
        where TInterceptor : class, IInterceptor
    {
        Intercept(registrator,typeof(TService),typeof(TInterceptor),typeof(TImplType),serviceKey);
    }
}

You’ll see how this extension class is used later on.

#4.1.4 Binding the Interceptor Registrars to the Event

When did Abp originally bind its interceptors to concrete types? It was when Castle Windsor registered a component: each interceptor registrar listened to the component registration event. When the event fired, each Abp interceptor registrar ran a series of checks to decide which interceptor the current type should be bound to.

Abp has 5 built-in interceptors: unit of work, parameter validation, authorization, audit logging and entity history. All five are set up when AbpBootstrapper runs its create method, and they listen to the component registration event at that point.

The problem now is that we don’t use Castle Windsor, so we can’t use IWindsorContainer to listen to the component registration event. DryIoc doesn’t have such an event either, so we move it up into IocManager: whenever one of the registration methods of IocManager is called, we raise an event explicitly to notify the interceptor registrars.

First go to the IIocManager interface and add a public delegate property. The delegate definition is below as well.

The delegate definition:

C#
using System;

namespace Abp.Dependency
{
    public delegate void RegisterTypeEventHandler(IIocManager iocManager, Type registerType,Type implementationType);
}

The property added to IIocManager:

C#
using System;
using DryIoc;

namespace Abp.Dependency
{
    /// <summary>
    /// Dependency injection container manager.
    /// This interface is used to perform injection operations.
    /// </summary>
    public interface IIocManager : IIocRegistrar, IIocResolver, IDisposable
    {
        IContainer IocContainer { get; }

        new bool IsRegistered(Type type);

        new bool IsRegistered<T>();

        event RegisterTypeEventHandler RegisterTypeEventHandler;
    }
}

After that, we raise this event explicitly inside the Register() methods of IocManager.

C#
public void Register(Type type, DependencyLifeStyle lifeStyle = DependencyLifeStyle.Singleton)
{
	IocContainer.Register(type,ApplyLifestyle(lifeStyle),
		made: Made.Of(FactoryMethod.ConstructorWithResolvableArguments));
	RegisterTypeEventHandler?.Invoke(this,type,type);
}

Like this, the event fires every time a component is registered. The Initialize() method of each registrar receives an IIocManager object, so all we need to do is change the original event subscription to our own event.

Here’s the unit of work interceptor registrar as an example:

C#
using System.Linq;
using System.Reflection;
using Abp.Dependency;
using Castle.Core;
using Castle.MicroKernel;

namespace Abp.Domain.Uow
{
    /// <summary>
    /// This class is used to register interceptor for needed classes for Unit Of Work mechanism.
    /// </summary>
    internal static class UnitOfWorkRegistrar
    {
        /// <summary>
        /// Initializes the registerer.
        /// </summary>
        /// <param name="iocManager">IOC manager</param>
        public static void Initialize(IIocManager iocManager)
        {
            iocManager.RegisterTypeEventHandler += (manager, type, implementationType) =>
            {
                var implType = implementationType.GetTypeInfo();

                HandleTypesWithUnitOfWorkAttribute(implType,manager);
                HandleConventionalUnitOfWorkTypes(iocManager, implType);
            };
        }

        private static void HandleTypesWithUnitOfWorkAttribute(TypeInfo implementationType,IIocManager iocManager)
        {
            if (IsUnitOfWorkType(implementationType) || AnyMethodHasUnitOfWork(implementationType))
            {
                // This uses the extension method we wrote above
                iocManager.IocContainer.Intercept(implementationType,typeof(UnitOfWorkInterceptor));
            }
        }

        private static void HandleConventionalUnitOfWorkTypes(IIocManager iocManager, TypeInfo implementationType)
        {
            if (!iocManager.IsRegistered<IUnitOfWorkDefaultOptions>())
            {
                return;
            }

            var uowOptions = iocManager.Resolve<IUnitOfWorkDefaultOptions>();

            if (uowOptions.IsConventionalUowClass(implementationType.AsType()))
            {
                // This uses the extension method we wrote above
                iocManager.IocContainer.Intercept(implementationType,typeof(UnitOfWorkInterceptor));
            }
        }

        private static bool IsUnitOfWorkType(TypeInfo implementationType)
        {
            return UnitOfWorkHelper.HasUnitOfWorkAttribute(implementationType);
        }

        private static bool AnyMethodHasUnitOfWork(TypeInfo implementationType)
        {
            return implementationType
                .GetMethods(BindingFlags.Instance | BindingFlags.Public | BindingFlags.NonPublic)
                .Any(UnitOfWorkHelper.HasUnitOfWorkAttribute);
        }
    }
}

Follow the same steps for the rest of the interceptor registrars.

            {
                iocManager.IocContainer.UseInstance<IEventBus>(EventBus.Default);
            }
            else
            {
                iocManager.IocContainer.Register<IEventBus,EventBus>(Reuse.Singleton);
            }

            _eventBus = iocManager.Resolve<IEventBus>();
            iocManager.RegisterTypeEventHandler += (manager, type, implementationType) =>
            {
                if (!typeof(IEventHandler).GetTypeInfo().IsAssignableFrom(implementationType))
                {
                    return;
                }

                var interfaces = implementationType.GetTypeInfo().GetInterfaces();
                foreach (var @interface in interfaces)
                {
                    if (!typeof(IEventHandler).GetTypeInfo().IsAssignableFrom(@interface))
                    {
                        continue;
                    }

                    var genericArgs = @interface.GetGenericArguments();
                    if (genericArgs.Length == 1)
                    {
                        _eventBus.Register(genericArgs[0], new IocHandlerFactory(_iocResolver, implementationType));
                    }
                }
            };
        }
    }
}

#4.3 Changing ASP.NET Core Related Code

So far we’ve made a few not-so-big changes to the Abp core library and the EF Core library. The only thing left is the Abp.AspNetCore library. .NET Core has its own DI framework. As I mentioned in the earlier source code analysis, if you change the return value of the ConfigureService() method of the Startup class to IServiceProvider, you can replace the built-in DI framework with another one.

In the AbpServiceCollectionExtensions extension class of the original Abp.AspNetCore library, you can see this code:

C#
public static IServiceProvider AddAbp<TStartupModule>(this IServiceCollection services, [CanBeNull] Action<AbpBootstrapperOptions> optionsAction = null)
	where TStartupModule : AbpModule
{
	var abpBootstrapper = AddAbpBootstrapper<TStartupModule>(services, optionsAction);

	ConfigureAspNetCore(services, abpBootstrapper.IocManager);

	return WindsorRegistrationHelper.CreateServiceProvider(abpBootstrapper.IocManager.IocContainer, services);
}

Here Abp uses the WindsorRegistrationHelper class to create and return an IServiceProvider. Does DryIoc give us something similar? It does. DryIoc provides an adapter in DryIoc.Microsoft.DependencyInjection, which can create an IServiceProvier based on DryIoc to replace the default DI framework.

First add the DryIoc.Microsoft.DependencyInjection NuGet package to the Abp.AspNetCore library, then edit the method above:

C#
public static IServiceProvider AddAbp<TStartupModule>(this IServiceCollection services, [CanBeNull] Action<AbpBootstrapperOptions> optionsAction = null)
	where TStartupModule : AbpModule
{
	var abpBootstrapper = AddAbpBootstrapper<TStartupModule>(services, optionsAction);

	ConfigureAspNetCore(services, abpBootstrapper.IocManager);

	var newContainer = new Container(rules =>
			rules.WithAutoConcreteTypeResolution())
		.WithDependencyInjectionAdapter(services);
	
	abpBootstrapper.IocManager.InitializeInternalContainer(newContainer);
	
	return abpBootstrapper.IocManager.IocContainer.BuildServiceProvider();
}

#4.3.1 Automatic Registration of View Components and Other Components

Besides the problem above, the Abp.AspNetCore library has a registrar, AbpAspNetCoreConventionalRegistrar, which also uses the registration method of the IWindsorContainer interface. That needs to change too.

using System.Linq;

using Microsoft.AspNetCore.Mvc;

namespace Abp.AspNetCore
{
    public class AbpAspNetCoreConventionalRegistrar : IConventionalDependencyRegistrar
    {
        public void RegisterAssembly(IConventionalRegistrationContext context)
        {
            //ViewComponents
            var types = context.Assembly.GetTypes()
                .AsParallel()
                .Where(type => typeof(ViewComponent).IsAssignableFrom(type))
                .Where(type => !type.IsGenericTypeDefinition)
                .Where(type => !type.IsAbstract)
                .AsSequential();

            foreach (var type in types)
            {
                context.IocManager.Register(type);
            }
        }
    }
}

#5. Known Issues

#5.1 Property Injection Doesn’t Work in ApplicationService

In the sample project, I created a TestApplicationService in the AspNetCoreApp.Application library. It has a GetJson() method.

Inside it, I use the AbpSession property from the base class. Normally the implementation of that property should be ClaimsAbpSession, but after testing I got this result:

As you can see, it was filled with the default empty implementation. The reason is that when DryIoc registers an object, you have to ask for property injection explicitly. Otherwise property injection is off by default.

Because of this, we add an isAutoInjectProperty parameter to the Register() methods on IIocRegistrar and IocManager, which decides whether to turn on property injection at registration time.

C#
public interface IIocRegistrar
{
	/// <summary>
	/// Registers a type as self registration.
	/// </summary>
	/// <typeparam name="T">Type of the class</typeparam>
	/// <param name="lifeStyle">Lifestyle of the objects of this type</param>
	void Register<T>(DependencyLifeStyle lifeStyle = DependencyLifeStyle.Singleton,bool isAutoInjectProperty = false)
		where T : class;

	/// <summary>
	/// Registers a type as self registration.
	/// </summary>
	/// <param name="type">Type of the class</param>
	/// <param name="lifeStyle">Lifestyle of the objects of this type</param>
	void Register(Type type, DependencyLifeStyle lifeStyle = DependencyLifeStyle.Singleton,bool isAutoInjectProperty = false);

	/// <summary>
	/// Registers a type with it's implementation.
	/// </summary>
	/// <typeparam name="TType">Registering type</typeparam>
	/// <typeparam name="TImpl">The type that implements <see cref="TType"/></typeparam>
	/// <param name="lifeStyle">Lifestyle of the objects of this type</param>
	void Register<TType, TImpl>(DependencyLifeStyle lifeStyle = DependencyLifeStyle.Singleton,bool isAutoInjectProperty = false)
		where TType : class
		where TImpl : class, TType;

	/// <summary>
	/// Registers a type with it's implementation.
	/// </summary>
	/// <param name="type">Type of the class</param>
	/// <param name="impl">The type that implements <paramref name="type"/></param>
	/// <param name="lifeStyle">Lifestyle of the objects of this type</param>
	void Register(Type type, Type impl, DependencyLifeStyle lifeStyle = DependencyLifeStyle.Singleton,bool isAutoInjectProperty = false);
}

The implementation then uses isAutoInjectProperty to decide whether to enable property injection. Here’s one Register() method as an example.

C#
public void Register(Type type, DependencyLifeStyle lifeStyle = DependencyLifeStyle.Singleton,bool isAutoInjectProperty = false)
{
	IocContainer.Register(type,
		ApplyLifestyle(lifeStyle),
		made: Made.Of(FactoryMethod.ConstructorWithResolvableArguments,
			propertiesAndFields: isAutoInjectProperty
				? PropertiesAndFields.Auto
				: null));
	RegisterTypeEventHandler?.Invoke(this,
		type,
		type);
}

Now go back to the BasicConventionalRegistrar registrar. Application services are all transient objects and all inherit from the IApplicationService interface. So we add a check: if the type is an application service, property injection is allowed when it is registered.

C#
public class BasicConventionalRegistrar : IConventionalDependencyRegistrar

	public void RegisterAssembly(IConventionalRegistrationContext context)

#6. Conclusion

The post makes the whole process look simple and easy, but I ran into quite a few pitfalls when I did it. Together with my earlier Abp source code analysis posts, this should help you understand the structure of the whole Abp framework better.

This way, you aren’t limited to DryIoc. You can swap in whatever other DI framework you like.

In Abp vNext, the IoC container is designed to be easy to replace, so you won’t have to go through this kind of trouble any more.

PS: The official project already has extensions for AutoFac and Castle Windsor.

The finished code and the demo are on GitHub: https://github.com/GameBelial/Abp-DryIoc.git
